## Run Input and Environment Binding

Task 3 preserves releaseId, testPlan and deviceSelector in the strict CreateTestRun request without adding arbitrary client device paths or environment assertions. Explicit server configuration selects the registered Agent/Device and supplies bounded CONFIG content for the single-device demonstration. Creation checks project, selector and capabilities, computes the actual CONFIG bytes digest, and freezes the Environment only after matching the CONFIG checksum in the Locked Manifest. Configuration is not a second authority for Release contents. Missing, mismatched or unsupported inputs are explicitly rejected; the ordinary Backend default INCOMPLETE payload-verification policy remains unchanged. This choice reuses existing configuration and PostgreSQL without adding an environment service.

Configuration uses disabled-by-default `vsrqg.demo.smoke.enabled` and the same-prefix `agent-id`, `device-id` and `environment-config-base64`. The latter encodes the exact CONFIG bytes, limited to 64 KiB after decoding with a bounded encoded input as well; base64 is transport encoding, not encryption. CONFIG strictly contains bootSessionId, buildId and buildFingerprint, without credentials or raw device serials. Source configuration and the registered Device vehicle/platform must satisfy the request selector and Release scope.

## Task 5 Result Submission and Evidence Sealing Dependencies

Task 5 consumes the existing AttemptEvidence application port. Session metadata sealing does not depend on the local Payload switch. The Evidence module retains one real implementation and the same JdbcEvidenceRepository, allowing cancellation/deadline closure to seal existing Sessions while file storage is disabled. resolve requires actual bytes and explicitly fails with EVIDENCE_STORAGE_DISABLED when PayloadStore is unavailable, without a success-returning substitute. HTTP upload/download and file reconciliation retain the existing demonstration switch.

This keeps lifecycle behavior dependent on the existing application port, without Test Management reading Evidence tables directly or maintaining another sealing rule. Sessions are sealed with their original binding before the fencing generation changes, within the same commit boundary as terminal Result, Attempt, Run and Audit/Outbox. Default context tests without a database provide an explicit test double for the real metadata repository, without changing production missing-dependency behavior. The cost is metadata-port wiring in the default context and regression coverage for disabled file storage, existing Sessions, cancellation/deadlines and rollback.

The V13 single-Case demonstration restriction remains. One Run-completion policy checks every Published Case Resolution and every created Attempt, with optional Case/Attempt boundary tests. This slice neither expands the scheduler nor removes the single-Case data constraint. Existing Result idempotency, digest, lease and authorization semantics remain. Actual implementation and checks are in [result engineering verification](../../m3/attempt-result-verification.md).

Task 5 uses incremental V15 storage for the terminal result projection and inputDigest, frozen within the original transaction. Later queries read that fixed projection without recreating historical facts from missing Payloads or later integrity observations. Pre-migration terminal V13/V14 Runs retain their original rows; queries use the same pure projection/JCS function over frozen inputs and Results. SQL jsonb text does not substitute for JCS, and missing results are not invented. The snapshot-required marker exempts only already-terminal rows at migration; existing active and new Runs require terminal snapshots. The marker cannot subsequently change, and new inserts cannot bypass it with false. This preserves historical queries while adding incremental-migration and old/new-data compatibility checks.

Events follow their stored Command/Attempt binding and consecutive sequenceNo values starting at 1. Matching sequence/digest replays return the original acknowledgement; gaps or different digests explicitly conflict. Result requests gain no Command/sequence fields and are checked against the stored server stream. Preflight ERROR/BLOCKED needs no invented STARTED event; Agent SKIPPED is rejected when this demonstration has no published skip condition. Authorized late conflicts use a separate short transaction for isolated Audit with fixed ownership, code and digest only: no raw Payload or terminal-fact mutation, and Audit failure cannot silently mean diagnostics were saved. This transaction must not wait on business rows locked by its outer transaction and requires real database regression coverage.

Module dependencies remain one-way: the consuming Test Management application package owns the single AttemptEvidence / EvidenceResolution outbound port; Evidence implements it using the same repository. Source references are updated together without unused compatibility aliases. The existing exception-specific Evidence handler covers calls through other Controllers, so Test Management does not depend directly on Evidence exceptions. This minimal dependency inversion prevents a module cycle without changing port semantics or the frozen Core Contract; the cost is architecture, application, and HTTP regression coverage for port placement and handler scope.

## Task 6 Host Execution and Recovery Implementation

Task 6 host implementation, tests/build and independent reviews follow the current instruction and are complete; exact delivery status is in [host Agent verification](../../m3/host-agent-verification.md). Host configuration explicitly references aapt and apksigner.jar from existing Android Build Tools, invoking the JAR directly with the JVM to avoid a Windows batch shell. Fixed arguments check APK package, version, signature and checksum; ambiguous signature output or unreadable inputs prevent execution, without installing another SDK. This reuses existing tools and requires verification of output parsing and failure paths.

The complete result request is persisted before submission. If the server has become terminal but its response was lost, recovery may replay the identical durable Result PUT to confirm the original receipt; timestamps, Evidence IDs and digest must not be regenerated. Only a response matching the original binding and digest confirms local completion; rejection or invalid authority retains diagnostics without new Evidence writes, a new lease or replayed device actions. This confirmation follows Task 5 terminal idempotency; the original RecoveryPolicy still forbids new actions under expired leases. Both the previously accepted result and the never-accepted expired result must be tested.

Device exclusion requires one controlled execution account and a unique canonical serial. A hashed lock in the account directory covers separate processes and spool directories, while the spool holds its own exclusive journal lock. This does not guarantee exclusion across operating-system accounts or selector aliases; those requirements require changes to the lock scope and deployment configuration first. Windows uses file force and atomic replacement, without claiming unsupported JDK directory fsync or absolute persistence during power loss. All spool contents are retained, and insufficient space stops new work; the Agent README documents these limits and resource caps.

The actual device mixes SurfaceFlinger diagnostics into screencap stdout, so that stream cannot represent complete PNG bytes. Screenshots now use one temporary-file path: first confirm the fixed foreground component, derive `/data/local/tmp/vsrqg-smoke-<uuid>.png` from the bound Attempt with strict UUID validation, run `shell screencap -p <path>`, read bounded binary bytes with `exec-out cat <same-path>`, and finally run exact `shell rm -- <same-path>`. Compared with scanning for a PNG signature or retaining a stdout fallback, this preserves PNG validation and failure semantics without new configuration or collection authority. The cost is a device temporary file and extra commands, requiring cleanup after write/read failure, visible cleanup failure, and preservation of the primary exception with a suppressed cleanup exception when both fail. Reads remain capped at 8 MiB with bounded commands and a whitelist limited to the fixed UUID PNG path. This diagnostic is not formal Evidence or complete M3 acceptance.

## Task 7 Demo Configuration and Test Entry

The current implementation instruction starts integration engineering. Top-level fields follow the accepted plan; server strictly contains origin and lifecycle (START / EXISTING), with identity, device and tool details supplied through controlled configuration-file references. START launches only its owned local demo Backend with explicitly provided loopback PostgreSQL. EXISTING uses an authorized existing demo only through APIs, without initializing or stopping that service. Missing runtime prerequisites fail explicitly without installing a database or enabling Company.

Wrapper tests follow actual m1-demo.tests.ps1 native PowerShell assertions and command injection rather than the newer Pester syntax in the plan example. The same test source runs on Windows and CI, preserving nonzero exit, CONFIG_INVALID, absence of a report, scenario failure summaries, result associations and digest checks. The cost is maintaining bounded test processes and explicit failure diagnostics, verified by actual tests and independent review.

Cross-module M3 integration uses a separate m3IntegrationTest source set/task with explicitly built Agent/APK inputs; configuration, report and HTTP-boundary unit tests remain in default Backend test. Existing M1/M2 gain no implicit SDK or Agent build prerequisites, and missing M3 inputs must fail the explicit task. Production bootJar excludes demo/Agent runtime. Every explicit integration invocation disables up-to-date/build-cache reuse and retains its materials in a new invocation directory, rejecting repeated UUIDs. CI uploads only that invocation's directory so old successful reports or Payloads cannot contaminate a failed attempt. The cost is maintaining separate test classpath, evidence directory locations and CI entry wiring, requiring actual build verification.

START initialization may read and reuse exactly matching existing SYNTHETIC_DEMO project, Agent/Device, certificate bindings and published Plan/Case definitions. Partial, non-synthetic or conflicting state fails explicitly without rebinding, changing published content or guessing replacement IDs. A fresh scoped demo USER session may be created if required by the ephemeral JWT lifecycle. Mutable observations such as heartbeats are not immutable-definition matching fields; previous Run/Result/Evidence remain preserved. This lets normal, deterministic-failure and repeated demos use the same controlled identity, at the cost of real-database regression coverage for bootstrap matching/transactions and consecutive starts.

## Local Demo Runtime Preparation

The Owner's subsequent instruction to execute the next step authorizes local PostgreSQL/Backend dependencies on drive D; actual checks are in the [local runtime record](../../m3/local-runtime-verification.md). Use the same PostgreSQL 17.11 version as compose through the EDB Windows ZIP, running on demand under the current account with loopback-only listening, SCRAM authentication and a separate restricted application role. No Docker installation, service registration or global PATH changes. Native ZIP was chosen because this Windows host has no container runtime and the slice needs only one local database. The cost is operator ownership of binary provenance/version, start/stop, controlled directories and later backups instead of container packaging; actual NotSigned and local-digest verification limits must remain explicit.

The environment health probe directly reuses existing M3Config.read and M3DemoBootstrap.start without calling initialize or Agent. TLS uses local demo PKCS12 identities and a separate trust store without bypassing verification. It checks only health, unauthenticated API rejection and normal shutdown; it cannot replace real Smoke. The cost is dependence on demo classpath and existing startup APIs, requiring re-export/compilation and verification after source changes. This choice adds no product configuration, persistent launcher or quality authority.

## Choice and Alternatives

Task 7 bounded demonstrations may explicitly pass the optional Agent parameter `--until-attempt-acked=<UUID>`; the original continuous entry with six arguments remains unchanged. The target Attempt comes from this Run's formal API. The Agent reuses its existing AgentLoop, journal and receipt validation, exiting normally only after persisting RESULT_ACKED for that target. The coordinator waits within a deadline for natural exit with code zero before completing a successful summary. Server terminal state does not replace local receipt confirmation, and replaying old journal entries does not complete the current target. The CI fixture uses the same completion path and executes its assertions before exiting. This resolves the shutdown race between server commit and host confirmation without expanding Result/Quality authority. Its cost is regression coverage for CLI compatibility, the completion loop, process waiting and old-journal recovery.

Use a Kotlin/JVM 21 host Agent calling existing ADB and reusing the accepted Agent HTTPS pull/ACK/Event/Result protocol. The Agent is a separate CLI process with no direct Backend database access or authority to write final Quality Results. The existing Backend owns orchestration, identities, leases and authoritative records. No Broker or device pool is added.

| Option | Trade-off |
|---|---|
| Host Agent + ADB + minimal test APK | Recommended: execution is separate from the device, reuses JVM/ADB and retains host records when the device disconnects; ADB capabilities and interruption paths require verification. |
| Persistent on-device Agent | Adds background execution, permissions, upgrades and power-loss recovery that the first install/launch demonstration does not need. |
| Standalone ADB script producing success JSON | Easy to demonstrate but bypasses Run/Attempt, leases and formal Evidence associations; unsuitable as the product implementation. |

## APK and Build

Add an independent Android project under `demo/android-smoke/`. Use a single Java Activity and native TextView displaying fixed explanatory text and the current Attempt marker. No Compose, dependency injection, networking, accounts or background services. Package `com.ricezhou.vsrqg.smoke`, sole entry `.SmokeActivity`; accept only a UUID `attemptId` and fixed `normal` / `assertion-failure` modes, the latter exclusively a negative demonstration fixture.

Build baseline: AGP 8.7.3, Gradle 8.9, JDK 17, compileSdk/targetSdk 35, minSdk 26, Build Tools 34.0.0. This isolated APK build leaves Backend Kotlin 2.2.21 / Gradle 8.14.4 / JVM 21 unchanged. The official Android [compatibility table](https://developer.android.com/build/releases/agp-8-7-0-release-notes?hl=en) lists Gradle 8.9, JDK 17 and maximum API 35 for AGP 8.7; this is not claimed to be the latest version. The original design confirmed only ADB availability on PATH. Subsequent Task 1 verified SDK build readiness; device API Level remains unverified. Pin the Wrapper checksum and record actual SDK/signing-certificate digests during implementation; keys stay out of Git.

## Execution and Trust

ADB is an allowlisted execution mechanism, following the [official ADB documentation](https://developer.android.com/tools/adb). Allow only test-package installation, launch, scoped log/UI reads and screenshots on an explicitly selected device. Use process argument arrays, fixed package/Activity names, and no arbitrary shell, first-device selection, uninstall, data clearing, flashing or reboot. A same-name package with a different signature blocks execution; do not uninstall it automatically.

The Agent uses the existing independent mTLS identity contract. The server controls certificate-to-project/Device/Agent bindings. User JWTs cannot substitute for Agent identity; Agents cannot publish Plans, change Manifests or create Quality Results. The APK is an untrusted test subject providing an observation marker. The Agent asserts current launch, foreground component and UI marker before reporting Test Result; Release Gate decisions remain with the future Quality Engine.

Collect only this application's current Attempt, without reading unrelated device-wide log buffers. Capture a screenshot after confirming the test Activity is foreground. Personal notifications remain a risk requiring a clean demonstration device. Real Payloads remain in controlled local storage by default and are not automatically pushed to GitHub.

## Verification, Rollback and Boundaries

Verify build/lint, input rejection, installation/signature conflicts, launch/UI assertions, stale markers, ADB disconnection, process timeout, Agent restart and same-run Result/Evidence associations. Record CI fixture and real-device evidence separately. Stopping the Agent stops new work; retain database history/spool and do not uninstall automatically.

This decision does not approve all M3, a real vehicle Release or Issue Verified. Test Run still fixes Release/Locked Manifest/Plan/Environment. Synthetic demonstration Releases must declare their tested scope; a test APK is not a complete vehicle Release. TDR-025 separately covers Evidence storage. Reevaluate for device pools, other APKs, flashing or an on-device Agent.
