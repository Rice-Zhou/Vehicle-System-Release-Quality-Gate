# V0.1 → V0.2 Architecture Evolution Specification

- Project: Vehicle System Release Quality Gate
- Short Name: VSRQG
- Current Architecture: V0.1
- Target Architecture: V0.2
- Status: DESIGN BASELINE
- Date: 2026-08-21

## 1. Purpose

This document defines how VSRQG evolves from the frozen V0.1 architecture into V0.2.

It does not replace:
- `docs/00-architecture-freeze.md`
- `docs/project-constitution.md`
- `docs/core-contract.md`
- `docs/system-architecture.md`

It defines the allowed direction of architectural evolution so that future AI coding agents, including Codex, do not independently redefine the project's original goals.

## 2. Architectural Position

V0.1 answers:

> What is VSRQG?

V0.2 answers:

> How should VSRQG be concretely implemented?

V0.3+ answers:

> How should VSRQG be productionized and scaled?

Therefore:

- V0.1 = Architecture Constitution
- V0.2 = Implementation Architecture
- V0.3+ = Production Evolution

## 3. Non-Negotiable Goal

VSRQG exists to establish an auditable, deterministic and evidence-driven quality gate for a complete automotive Android system release.

It must not degrade into only:
- an automated test framework
- a Jira dashboard
- a Crash dashboard
- an APK verification tool
- a CI dashboard
- an AI report generator

Those are capabilities of VSRQG, not its definition.

## 4. V0.2 Architectural Principles

### 4.1 Release-Centric

Release remains the highest-level delivery unit.

An APK is an Artifact. A Test Run verifies a Release. A Quality Result evaluates a Release.

### 4.2 Evidence-Driven

Every important quality claim must have traceable evidence, including Crash, ANR, Memory, CPU, FPS, test results, screenshots, logs, Perfetto traces and dumps where applicable.

### 4.3 Traceability-First

The fundamental logical chain remains:

```text
Issue → Commit → Build → Artifact → Release → Test Run → Test Result → Evidence
```

Implementation may add intermediate entities, but the logical chain must remain available.

### 4.4 Deterministic Quality Decision

The final Release decision must be reproducible from the same input snapshot and rule version.

```text
QualityResult =
  Evaluate(
    Release,
    Manifest,
    Traceability,
    TestResults,
    Evidence,
    QualityRules
  )
```

### 4.5 External-System Isolation

Jira and internal issue systems are external systems and must be accessed through adapters. The Core Domain must not depend on their proprietary data models.

### 4.6 Real Device Authority

For runtime claims, real-device evidence is authoritative where a Release Gate criterion explicitly requires real hardware.

### 4.7 AI Is Advisory

AI may classify, summarize, cluster, recommend and explain. It must not become the authoritative deterministic Release Gate decision engine in V0.2.

## 7. Recommended V0.2 Deployment Model

Use a modular monolith or a small number of well-defined services initially.

Do not introduce microservices merely because the system has multiple conceptual modules.

Priorities:
1. clear domain boundaries
2. stable APIs
3. testability
4. traceability
5. deployability
6. operational simplicity

Services may be extracted later only for concrete scaling, isolation or reliability reasons.

These remain Core Contract concepts:

- Release

- Issue

- Build

- Test Case

V0.2 may refine fields and relationships but must not remove their conceptual responsibilities.

## 9. Release Domain

### 9.1 Release Lifecycle

Recommended conceptual states:

```text
DRAFT
  ↓
REGISTERED
  ↓
READY_FOR_TEST
  ↓
TESTING
  ↓
QUALITY_EVALUATED
  ↓
PASS / BLOCKED
```

Additional operational states may be introduced if necessary, but transitions must be explicit.

### 9.2 Release Identity

Release identity must be independent from Jira version, Git branch, APK version and build number. Those systems may be referenced but must not define the Release identity.

## 10. Release Manifest Evolution

The Manifest must answer:

> Exactly what is inside this Release?

It should support:
- APKs
- system images
- vendor images
- firmware
- configuration
- third-party components
- versions
- build information
- source information
- checksums

### 10.1 Manifest Immutability

Once a Release enters testing, its Manifest should become immutable.

If contents change, create a new Manifest revision or new Release. Never silently replace an artifact under an already-tested Release.

## 11. Artifact Identity

Each Artifact must have a stable identity.

For Android APKs, recommended information:
- packageName
- versionName
- versionCode
- signing certificate fingerprint
- checksum
- buildId
- source repository
- commit

For system images:
- image type
- build ID
- checksum
- source build
- version

For third-party components:
- supplier
- supplier version
- checksum
- acquisition source

## 12. Issue Architecture

Multiple issue sources are required.

```text
                Issue Adapter
                     |
          +----------+----------+
          v                     v
        Jira              Internal Issue
          |                     |
          +----------+----------+
                     v
              Normalized Issue
```

The Core Domain sees only the normalized Issue model.

## 13. Issue Snapshot

Issue data must be snapshotted for Release evaluation.

Historical Release evaluation must not depend on the current live state of Jira or another issue system.

Example: if a Release was evaluated on August 20, later changes to Jira on August 25 must not silently change the historical Release result.

## 14. Fixed / Included / Verified

These are explicit concepts.

### Fixed

A valid source-level fix exists.

### Included

The fix is demonstrably included in the target Release.

### Verified

The fix has been tested against the target Release and satisfies its verification requirement.

Therefore:

```text
Commit exists ≠ Fix included
Fix included ≠ Fix verified
```

## 15. Traceability Architecture

Minimum source chain:

```text
Issue → Commit → Build → Artifact → Release
```

Verification chain:

```text
Release → Test Run → Test Result → Evidence
```

Combined:

```text
Issue → Commit → Build → Artifact → Release
                                  |
                                  v
                              Test Run
                                  |
                                  v
                              Test Result
                                  |
                                  v
                               Evidence
```

## 16. Traceability Confidence

V0.2 may support confidence states:

- HIGH
- MEDIUM
- LOW
- UNKNOWN

Confidence indicates the strength of available proof; it never replaces factual evidence.

Example:
- Build metadata directly links a commit to a build → HIGH
- Artifact association inferred only from version naming → LOW

## 17. Test Architecture

Testing is separated into:

1. Test Definition
2. Test Execution
3. Evidence Collection
4. Result Evaluation

These responsibilities must remain distinct.

## 18. Test Plan

A Test Plan defines what should be tested and is versioned.

Example Release Smoke Test:
- boot
- launcher
- navigation
- Bluetooth
- Wi-Fi
- media
- key system functions

## 19. Test Case

A Test Case has a stable identity and version.

Recommended fields:
- testCaseId
- version
- preconditions
- steps
- expectedResult
- requiredEvidence
- timeout
- retryPolicy

## 20. Test Run

A Test Run represents one actual execution and links:
- Release
- Test Plan
- Test Agent
- Device
- Environment
- start time
- end time
- result

## 21. Real Device Model

V0.2 should introduce a Device entity.

Recommended conceptual fields:
- deviceId
- hardwareModel
- serialNumber/reference
- Android version
- firmware version
- vehicle/platform
- bench
- status
- capabilities

Sensitive identifiers must follow company security policy.

## 22. Test Agent

The Test Agent is the execution-side component.

```text
Test Orchestrator
       |
       | command
       v
   Test Agent
       |
       +-- Test Executor
       +-- Log Collector
       +-- Crash Collector
       +-- ANR Collector
       +-- Memory Collector
       +-- Screenshot Collector
       +-- Performance Collector
```

Collectors should be plugin-like capabilities.

## 23. Test Agent Principle

The Agent does not own Release Quality decisions.

It collects actions, results, metrics and evidence.

The server-side Quality Engine decides the Release quality result.

## 24. Crash Collection

V0.2 should support:
- Android crash logs
- tombstones where accessible
- application process crashes
- system-server related crashes where relevant

Crash evidence should include:
- timestamp
- process/package
- version
- stack information
- device
- Release
- Test Run
- raw evidence reference

## 25. ANR Collection

ANR collection should capture:
- package/process
- timestamp
- reason
- traces
- duration where available
- Release
- Test Run
- device

ANR evidence remains independent from the final Quality Result.

## 26. Memory Collection

V0.2 should define a Memory Collector interface.

It may collect:
- PSS
- RSS
- Java heap
- native heap where available
- process-level memory
- system memory

Collectors must not hard-code Release policy.

Example:

```text
Collector:
Process PSS = 420 MB

Quality Rule:
Critical app PSS > 400 MB for 3 consecutive samples → BLOCK
```

This separation is mandatory.

## 27. Evidence Architecture

Evidence is divided conceptually into:

### Metadata

Stored in structured database.

### Payload

Stored in object/file storage.

Example:

```text
Evidence
 ├── evidenceId
 ├── type
 ├── timestamp
 ├── Release
 ├── TestRun
 ├── TestResult
 ├── checksum
 └── payloadUri
```

Large logs and traces should not normally be stored directly inside relational database fields.

## 28. Evidence Integrity

Evidence should have:
- checksum
- creation timestamp
- source
- associated Release
- associated Test Run
- collector version

Evidence should be tamper-evident where practical.

## 29. Quality Engine

The Quality Engine evaluates normalized facts.

```text
                 Facts
                   |
       +-----------+-----------+
       v           v           v
    Manifest   Test Result  Traceability
       |           |           |
       +-----------+-----------+
                   |
              Rule Engine
                   |
             Rule Evaluation
                   |
              Quality Result
```

## 30. Quality Rule Separation

Rules must not be embedded inside:
- Test Agent
- Jira Adapter
- Manifest Parser
- Test Executor

Rules belong to the Quality Engine.

## 31. Quality Rule Example

```text
RULE: CRITICAL_ANR

WHEN:
    ANR.count(severity=CRITICAL) > 0

THEN:
    BLOCK

REASON:
    Critical ANR detected during Release validation
```

Another example:

```text
RULE: REQUIRED_ISSUE_NOT_VERIFIED

WHEN:
    issue.required = true
    AND issue.verificationStatus != VERIFIED

THEN:
    BLOCK
```

## 32. Quality Result

Quality Result preserves:
- releaseId
- ruleSetId
- ruleSetVersion
- evaluationId
- timestamp
- rule outcomes
- evidence references
- final status

It must be reproducible.

## 33. Quality Status

Minimum:
- PASS
- WARNING
- BLOCK

Optional internal states:
- NOT_EVALUATED
- ERROR

ERROR must never silently become PASS.

## 34. Rule Priority

Recommended:

```text
BLOCK
  >
WARNING
  >
PASS
```

A single BLOCK rule may prevent Release PASS.

## 35. Quality Rule Versioning

Rules are versioned.

Example:
- `CRITICAL_ANR:v1`
- `CRITICAL_ANR:v2`

Historical Releases continue to reference the rule version used for their evaluation.

## 36. API Architecture

V0.2 should expose APIs around domain concepts.

Example:

```text
/releases
/releases/{releaseId}
/releases/{releaseId}/manifest
/releases/{releaseId}/issues
/releases/{releaseId}/traceability
/releases/{releaseId}/test-runs
/releases/{releaseId}/quality-result
```

Exact API technology is not frozen. REST is acceptable for MVP.

## 37. Event Architecture

Events may be introduced for asynchronous processing.

Examples:
- ReleaseCreated
- ManifestLocked
- TestRunStarted
- TestRunCompleted
- EvidenceCollected
- QualityEvaluationRequested
- QualityEvaluationCompleted

Events must not replace Core Contract entities.

## 38. Storage Architecture

Recommended MVP:

```text
PostgreSQL
    +
Object Storage
```

PostgreSQL:
- domain entities
- relationships
- metadata
- Quality Results

Object Storage:
- logs
- traces
- screenshots
- dumps
- large evidence

## 39. CI / Build Integration

VSRQG consumes existing build-system information rather than replacing the build system.

Build systems provide:
- build identity
- source revision
- artifacts
- build metadata

## 40. Jira Integration

Jira remains an Adapter responsible for:
- authentication
- querying
- pagination
- mapping
- synchronization
- source references

The Core Domain receives normalized Issue objects.

## 41. Internal Issue System Integration

The internal issue system follows the same adapter contract as Jira.

The Quality Engine must not know whether an Issue originated from Jira, an internal issue system or a future system.

## 42. Authentication

V0.2 should introduce:
- user identity
- roles
- service credentials
- device credentials
- adapter credentials

Secrets must not be stored in Git, Manifest, source code or logs.

## 43. Auditability

Important actions should be auditable:
- Release creation
- Manifest lock
- Manifest change
- Test execution
- Quality evaluation
- Quality override
- Release approval

Manual override must record who, when, what and why.

## 44. MVP Boundary

V0.2 should prioritize:

1. Release
2. Manifest
3. Artifact
4. Issue
5. Traceability
6. Device
7. Test Plan
8. Test Run
9. Evidence
10. Quality Rule
11. Quality Result

The following must not block MVP:
- advanced AI
- predictive analytics
- large-scale distributed execution
- complex microservices
- full vehicle feature automation

## 45. Architecture Evolution Rules

Codex may:
- refine fields
- refine interfaces
- propose implementation technologies
- propose database indexes
- propose API structures
- propose plugin interfaces
- propose deployment details

Codex must not:
- redefine Release
- remove Manifest
- remove Evidence
- remove Traceability
- make Jira the Core Domain
- make AI the final decision maker
- merge Fixed/Included/Verified into one status
- bypass Quality Engine
- bypass ADR process

## 46. ADR Trigger Conditions

Codex must stop implementation and propose an ADR if a design requires:
- changing Core Contract
- changing Release identity
- changing Manifest semantics
- changing Traceability semantics
- changing Quality decision semantics
- replacing deterministic Quality Gate with AI
- removing Evidence as a first-class concept
- changing ownership between core modules

After design review, V0.2 itself should become frozen.

```text
V0.2 Design Freeze
        ↓
Implementation
        ↓
Integration Testing
        ↓
MVP Release
        ↓
```

V0.2 implementation must not continuously redefine the architecture.

## 50. Final Principle

The project must evolve through controlled architecture increments.

> Design first. Freeze second. Implement third. Measure fourth. Evolve fifth.

Never allow implementation convenience to silently redefine the business architecture.
