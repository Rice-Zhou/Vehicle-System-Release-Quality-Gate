# V0.1 → V0.2 架构演进规范

- Project：Vehicle System Release Quality Gate
- Short Name：VSRQG
- Current Architecture：V0.1
- Target Architecture：V0.2
- Status：DESIGN BASELINE
- Date：2026-08-21

## 1. 目的

本文档定义 VSRQG 如何从已冻结的 V0.1 架构演进至 V0.2。

它不取代：

- `docs/00-architecture-freeze.md`
- `docs/project-constitution.md`
- `docs/core-contract.md`
- `docs/system-architecture.md`

它定义允许的架构演进方向，避免包括 Codex 在内的未来 AI Coding Agent 独立重新定义项目原始目标。

## 2. 架构定位

V0.1 回答：

> VSRQG 是什么？

V0.2 回答：

> VSRQG 应当如何具体实现？

V0.3+ 回答：

> VSRQG 应当如何生产化并扩展？

因此：

- V0.1 = Architecture Constitution
- V0.2 = Implementation Architecture
- V0.3+ = Production Evolution

## 3. 不可协商的目标

VSRQG 的存在是为了针对完整的汽车 Android 系统 Release，建立可审计、确定性且由 Evidence 驱动的 Quality Gate。

它不得退化为：

- 自动化 Test Framework
- Jira Dashboard
- Crash Dashboard
- APK Verification Tool
- CI Dashboard
- AI Report Generator

这些是 VSRQG 的能力，而不是其定义。

## 4. V0.2 架构原则

### 4.1 Release-centric

Release 仍是最高层级的交付单元。

APK 是 Artifact。Test Run 验证 Release。Quality Result 评估 Release。

### 4.2 Evidence-driven

每项重要质量主张都必须具有可追溯 Evidence，包括适用场景下的 Crash、ANR、Memory、CPU、FPS、Test Result、Screenshot、Log、Perfetto Trace 和 Dump。

### 4.3 Traceability-first

基础逻辑链路保持不变：

```text
Issue → Commit → Build → Artifact → Release → Test Run → Test Result → Evidence
```

实现可以增加中间实体，但必须始终能够得到该逻辑链路。

### 4.4 确定性质量决策

使用相同 Input Snapshot 和 Rule Version 时，最终 Release 决策必须可复现。

```text
QualityResult =
  Evaluate(
    Release,
    Manifest,
    Traceability,
    TestResults,
    Evidence,
    QualityRules
  )
```

### 4.5 外部系统隔离

Jira 和内部 Issue 系统属于外部系统，必须通过 Adapter 访问。Core Domain 不得依赖其专有数据模型。

### 4.6 真实设备权威性

当 Release Gate 标准明确要求真实硬件时，运行时主张以真实设备 Evidence 为权威依据。

### 4.7 AI 仅提供咨询

AI 可以分类、总结、聚类、建议和解释。在 V0.2 中，它不得成为权威的确定性 Release Gate 决策引擎。

## 7. 推荐的 V0.2 部署模型

初期采用 Modular Monolith 或少量边界清晰的 Service。

不得仅因系统存在多个概念模块便引入 Microservice。

优先级：

1. 清晰的 Domain Boundary
2. 稳定的 API
3. 可测试性
4. Traceability
5. 可部署性
6. 运维简单性

以后仅在存在具体的扩展、隔离或可靠性原因时提取 Service。

## 8. Core Domain 演进

以下内容仍是 Core Contract 概念：

- Release
- Release Manifest
- Artifact
- Issue
- Commit
- Build
- Test Plan
- Test Case
- Test Run
- Test Result
- Evidence
- Traceability
- Quality Rule
- Quality Result

V0.2 可以细化字段与关系，但不得移除其概念职责。

## 9. Release Domain

### 9.1 Release 生命周期

推荐的概念状态：

```text
DRAFT
  ↓
REGISTERED
  ↓
READY_FOR_TEST
  ↓
TESTING
  ↓
QUALITY_EVALUATED
  ↓
PASS / BLOCKED
```

必要时可以增加运行状态，但状态转换必须显式定义。

### 9.2 Release Identity

Release Identity 必须独立于 Jira Version、Git Branch、APK Version 和 Build Number。可以引用这些系统，但它们不得定义 Release Identity。

## 10. Release Manifest 演进

Manifest 必须回答：

> 这个 Release 中确切包含什么？

它应支持：

- APK
- System Image
- Vendor Image
- Firmware
- Configuration
- 第三方 Component
- Version
- Build Information
- Source Information
- Checksum

### 10.1 Manifest 不可变性

Release 一旦进入 Testing，其 Manifest 应变为不可变。

如果内容发生变化，必须创建新的 Manifest Revision 或新的 Release。不得在已经测试的 Release 下静默替换 Artifact。

## 11. Artifact Identity

每个 Artifact 必须具有稳定身份。

Android APK 的推荐信息：

- packageName
- versionName
- versionCode
- signing certificate fingerprint
- checksum
- buildId
- source repository
- commit

System Image 的推荐信息：

- image type
- build ID
- checksum
- source build
- version

第三方 Component 的推荐信息：

- supplier
- supplier version
- checksum
- acquisition source

## 12. Issue 架构

必须支持多个 Issue Source。

```text
                Issue Adapter
                     |
          +----------+----------+
          v                     v
        Jira              Internal Issue
          |                     |
          +----------+----------+
                     v
              Normalized Issue
```

Core Domain 只接收 Normalized Issue Model。

## 13. Issue Snapshot

用于 Release 评估的 Issue 数据必须形成 Snapshot。

历史 Release 评估不得依赖 Jira 或其他 Issue System 当前的实时状态。

例如：如果一个 Release 于 8 月 20 日完成评估，Jira 在 8 月 25 日发生的修改不得静默改变该历史 Release Result。

## 14. Fixed / Included / Verified

三者是显式概念。

### Fixed

存在有效的源代码级修复。

### Included

能够证明该修复已包含在目标 Release 中。

### Verified

已针对目标 Release 测试该修复，且满足其验证要求。

因此：

```text
Commit exists ≠ Fix included
Fix included ≠ Fix verified
```

## 15. Traceability 架构

最小 Source Chain：

```text
Issue → Commit → Build → Artifact → Release
```

Verification Chain：

```text
Release → Test Run → Test Result → Evidence
```

组合链路：

```text
Issue → Commit → Build → Artifact → Release
                                  |
                                  v
                              Test Run
                                  |
                                  v
                              Test Result
                                  |
                                  v
                               Evidence
```

## 16. Traceability Confidence

V0.2 可以支持以下 Confidence State：

- HIGH
- MEDIUM
- LOW
- UNKNOWN

Confidence 表示已有证明的强度；它永远不能取代事实 Evidence。

示例：

- Build Metadata 将 Commit 直接关联至 Build → HIGH
- 仅根据 Version Naming 推断 Artifact 关联 → LOW

## 17. Test 架构

Test 分为：

1. Test Definition
2. Test Execution
3. Evidence Collection
4. Result Evaluation

这些职责必须保持分离。

## 18. Test Plan

Test Plan 定义应测试什么，并且必须版本化。

Release Smoke Test 示例：

- boot
- launcher
- navigation
- Bluetooth
- Wi-Fi
- media
- key system functions

## 19. Test Case

Test Case 具有稳定 Identity 和 Version。

推荐字段：

- testCaseId
- version
- preconditions
- steps
- expectedResult
- requiredEvidence
- timeout
- retryPolicy

## 20. Test Run

Test Run 表示一次实际执行，并关联：

- Release
- Test Plan
- Test Agent
- Device
- Environment
- start time
- end time
- result

## 21. 真实设备模型

V0.2 应引入 Device Entity。

推荐概念字段：

- deviceId
- hardwareModel
- serialNumber/reference
- Android version
- firmware version
- vehicle/platform
- bench
- status
- capabilities

敏感 Identifier 必须遵循公司安全政策。

## 22. Test Agent

Test Agent 是执行侧组件。

```text
Test Orchestrator
       |
       | command
       v
   Test Agent
       |
       +-- Test Executor
       +-- Log Collector
       +-- Crash Collector
       +-- ANR Collector
       +-- Memory Collector
       +-- Screenshot Collector
       +-- Performance Collector
```

Collector 应作为 Plugin-like Capability。

## 23. Test Agent 原则

Agent 不负责 Release Quality 决策。

它收集 Action、Result、Metric 和 Evidence。

服务端 Quality Engine 决定 Release Quality Result。

## 24. Crash 采集

V0.2 应支持：

- Android Crash Log
- 可访问时的 Tombstone
- Application Process Crash
- 相关场景下的 system-server Crash

Crash Evidence 应包括：

- timestamp
- process/package
- version
- stack information
- device
- Release
- Test Run
- raw evidence reference

## 25. ANR 采集

ANR 采集应包含：

- package/process
- timestamp
- reason
- traces
- 可获取时的 duration
- Release
- Test Run
- device

ANR Evidence 与最终 Quality Result 保持独立。

## 26. Memory 采集

V0.2 应定义 Memory Collector Interface。

它可以采集：

- PSS
- RSS
- Java heap
- 可获取时的 native heap
- process-level memory
- system memory

Collector 不得硬编码 Release Policy。

示例：

```text
Collector:
Process PSS = 420 MB

Quality Rule:
Critical app PSS > 400 MB for 3 consecutive samples → BLOCK
```

这种分离是强制要求。

## 27. Evidence 架构

Evidence 在概念上分为：

### Metadata

存储于结构化 Database。

### Payload

存储于 Object/File Storage。

示例：

```text
Evidence
 ├── evidenceId
 ├── type
 ├── timestamp
 ├── Release
 ├── TestRun
 ├── TestResult
 ├── checksum
 └── payloadUri
```

大型 Log 和 Trace 通常不应直接存储在 Relational Database Field 中。

## 28. Evidence 完整性

Evidence 应具有：

- checksum
- creation timestamp
- source
- associated Release
- associated Test Run
- collector version

在实际可行时，Evidence 应具备篡改可检测性。

## 29. Quality Engine

Quality Engine 评估 Normalized Fact。

```text
                 Facts
                   |
       +-----------+-----------+
       v           v           v
    Manifest   Test Result  Traceability
       |           |           |
       +-----------+-----------+
                   |
              Rule Engine
                   |
             Rule Evaluation
                   |
              Quality Result
```

## 30. Quality Rule 分离

Rule 不得嵌入：

- Test Agent
- Jira Adapter
- Manifest Parser
- Test Executor

Rule 归 Quality Engine 所有。

## 31. Quality Rule 示例

```text
RULE: CRITICAL_ANR

WHEN:
    ANR.count(severity=CRITICAL) > 0

THEN:
    BLOCK

REASON:
    Critical ANR detected during Release validation
```

另一个示例：

```text
RULE: REQUIRED_ISSUE_NOT_VERIFIED

WHEN:
    issue.required = true
    AND issue.verificationStatus != VERIFIED

THEN:
    BLOCK
```

## 32. Quality Result

Quality Result 保留：

- releaseId
- ruleSetId
- ruleSetVersion
- evaluationId
- timestamp
- rule outcomes
- evidence references
- final status

它必须可复现。

## 33. Quality Status

最小集合：

- PASS
- WARNING
- BLOCK

可选内部状态：

- NOT_EVALUATED
- ERROR

ERROR 绝不能静默变为 PASS。

## 34. Rule 优先级

推荐：

```text
BLOCK
  >
WARNING
  >
PASS
```

一条 BLOCK Rule 即可阻止 Release PASS。

## 35. Quality Rule 版本管理

Rule 必须版本化。

示例：

- `CRITICAL_ANR:v1`
- `CRITICAL_ANR:v2`

历史 Release 继续引用评估时使用的 Rule Version。

## 36. API 架构

V0.2 应围绕 Domain Concept 暴露 API。

示例：

```text
/releases
/releases/{releaseId}
/releases/{releaseId}/manifest
/releases/{releaseId}/issues
/releases/{releaseId}/traceability
/releases/{releaseId}/test-runs
/releases/{releaseId}/quality-result
```

具体 API 技术不冻结。MVP 可以采用 REST。

## 37. Event 架构

可以引入 Event 进行异步处理。

示例：

- ReleaseCreated
- ManifestLocked
- TestRunStarted
- TestRunCompleted
- EvidenceCollected
- QualityEvaluationRequested
- QualityEvaluationCompleted

Event 不得取代 Core Contract Entity。

## 38. 存储架构

推荐的 MVP：

```text
PostgreSQL
    +
Object Storage
```

PostgreSQL 存储：

- Domain Entity
- Relationship
- Metadata
- Quality Result

Object Storage 存储：

- Log
- Trace
- Screenshot
- Dump
- 大型 Evidence

## 39. CI / Build 集成

VSRQG 使用现有 Build System 信息，而不是取代 Build System。

Build System 提供：

- build identity
- source revision
- artifacts
- build metadata

## 40. Jira 集成

Jira 仍是 Adapter，负责：

- authentication
- querying
- pagination
- mapping
- synchronization
- source references

Core Domain 接收 Normalized Issue Object。

## 41. 内部 Issue System 集成

内部 Issue System 遵循与 Jira 相同的 Adapter Contract。

Quality Engine 不得知道 Issue 来自 Jira、内部 Issue System 还是未来系统。

## 42. Authentication

V0.2 应引入：

- user identity
- roles
- service credentials
- device credentials
- adapter credentials

Secret 不得存储在 Git、Manifest、Source Code 或 Log 中。

## 43. 可审计性

重要 Action 应可审计：

- Release creation
- Manifest lock
- Manifest change
- Test execution
- Quality evaluation
- Quality override
- Release approval

Manual Override 必须记录由谁、何时、对什么内容以及为何执行。

## 44. MVP 边界

V0.2 应优先实现：

1. Release
2. Manifest
3. Artifact
4. Issue
5. Traceability
6. Device
7. Test Plan
8. Test Run
9. Evidence
10. Quality Rule
11. Quality Result

以下内容不得阻塞 MVP：

- Advanced AI
- Predictive Analytics
- Large-scale Distributed Execution
- Complex Microservice
- Full Vehicle Feature Automation

## 45. 架构演进规则

Codex 可以：

- 细化 Field
- 细化 Interface
- 提议 Implementation Technology
- 提议 Database Index
- 提议 API Structure
- 提议 Plugin Interface
- 提议 Deployment Detail

Codex 不得：

- 重新定义 Release
- 移除 Manifest
- 移除 Evidence
- 移除 Traceability
- 让 Jira 成为 Core Domain
- 让 AI 成为最终决策者
- 将 Fixed/Included/Verified 合并为一个状态
- 绕过 Quality Engine
- 绕过 ADR 流程

## 46. ADR 触发条件

如果一项设计要求以下任一事项，Codex 必须停止实施并提出 ADR：

- 修改 Core Contract
- 修改 Release Identity
- 修改 Manifest Semantics
- 修改 Traceability Semantics
- 修改 Quality Decision Semantics
- 用 AI 取代 Deterministic Quality Gate
- 移除 Evidence 一级概念
- 修改 Core Module 之间的职责归属

## 49. V0.2 Freeze

完成 Design Review 后，V0.2 本身应被冻结。

```text
V0.2 Design Freeze
        ↓
Implementation
        ↓
Integration Testing
        ↓
MVP Release
        ↓
Operational Feedback
        ↓
V0.3
```

V0.2 实施过程不得持续重新定义架构。

## 50. 最终原则

项目必须通过受控的架构增量演进。

> 先设计，后冻结；再实施，再度量；最后演进。

绝不允许实现便利性静默重定义业务架构。
