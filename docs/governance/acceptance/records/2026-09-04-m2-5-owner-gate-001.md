# M2.5 Traceability Verification Snapshot 验收候选记录

## Scope

**WHY**

M2.3 已固定 Release 的 Issue 集合，M2.4 已固定三类 typed Edge Revision。M2.5 候选需要证明系统能够只使用这些历史事实和 Locked Manifest authority，确定性生成可审计、可重放的 Fixed、Included、固定 `Verified=false` 与精确 Gap，并在故障后恢复而不改写历史。

**WHAT**

- 当前中文 Subject Commit `2652c7f442b84a6ed04865e0104bf01a6c45e69d` 与英文配对 Subject Commit `a1a86715d244965061e5d333ca04e26f92a5dc79` 上的 V11 Migration、异步 Verification Run、固定 Input Ledger、Worker、不可变 Snapshot、read/replay API，以及 Task 7 性能、恢复、Gate、CI 和运维规范。
- 20 个 Issue、2,000 条固定 Edge 的 Pilot 性能与常数级 query-count 验证。
- PostgreSQL `pg_dump` 到独立 PostgreSQL `pg_restore` 后，从恢复关系事实重算 Snapshot canonical digest；以严格更新的 `pg_postmaster_start_time()` 证明独立数据库真实 restart，再通过 fresh reconnect/repository reclaim RUNNING job；另覆盖 poison Dead Letter 与新 Run 人工 retry。
- 固定 12 步 fail-closed Gate、Evidence exact-property allowlist/secret 与绝对路径拒绝、summary/digest 和只读 GitHub Actions Artifact。

**BOUNDARY**

- 不改变 V0.1 Core Contract、Release-centric architecture、Locked Manifest authority、Evidence、Traceability、Deterministic Quality Engine、Adapter/Plugin 或 ADR 治理。
- M2.5 不读取 Jira、GitHub、CI、Device、Test Agent 或 Company 环境，不产生 `Verified=true`，不从最新 Revision、JSON、文件或缓存重建历史。
- 不授权 Company、真实 Provider、M3、`main`/`release` merge、Tag、release 或 production deployment。
- 共享 CI 的宽松性能硬上限只防算法退化，不代表 Company 性能承诺或 Company Ready。

**ACCEPTANCE**

Project Owner 只有在双语 Subject 固定、两个 exact-head Linux/Docker CI 均成功、两份 `m2-5-evidence-${commit}` Artifact 可用、Pair Gate 通过，并复核 V11、完整链/五类 Gap、transaction、concurrency、replay、recovery、security 与 20/2,000 性能 Evidence 后，才可给出 `APPROVE`、`CONDITIONAL` 或 `REJECT`。当前记录不代替 Owner 决策。
